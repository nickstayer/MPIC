# MPIC - Монитор Интеграции Почты и CRM

## Назначение

Приложение `MPIC` (Mail-CRM Integration Checker) представляет собой службу мониторинга, предназначенную для проверки корректности работы интеграции между почтовым ящиком и CRM-системой "Мегаплан".

Основная задача — автоматически отслеживать, создаются ли в Мегаплане сделки после получения писем от клиентов, и оперативно уведомлять ответственных лиц о сбоях и восстановлении работы интеграции.

## Структура решения

- **MPIC** — основной проект (служба мониторинга, точка входа).
- **MegaplanSync.Core** — минимальная библиотека для работы с API Мегаплана: клиент (`MegaApiClient`), сервис чтения сделок (`ApiService`), модели `Deal`/`Contractor`, нормализатор данных.
- **MegaplanSync.ApiClient** — HTTP-клиент API Мегаплана с кэшированием токена.
- **MegaplanSync.Logging** — файловый логгер.

`MegaplanSync` присутствует в решении только в объёме, необходимом MPIC для получения сделок из Мегаплана.

## Принцип работы

1.  **Периодическая проверка**: Приложение запускается через заданные интервалы времени.
2.  **Анализ почты**: На каждом цикле оно подключается к указанному в настройках почтовому ящику (по протоколу IMAP) и получает информацию о последнем входящем письме.
3.  **Запрос к CRM**: Затем приложение обращается к API Мегаплана и запрашивает список сделок, созданных после получения этого письма.
4.  **Проверка связи**: Система ищет сделку, контактные данные контрагента в которой (email) совпадают с адресом отправителя письма.
5.  **Определение статуса**:
    *   **Успех**: Если сделка найдена и была создана в течение заданного порогового времени, интеграция считается работающей.
    *   **Предупреждение**: Если сделка найдена, но создана с задержкой, превышающей пороговое значение, система отправляет предупреждение.
    *   **Сбой**: Если в течение порогового времени соответствующая сделка не была найдена, система фиксирует сбой интеграции.

## Логика уведомлений

Система уведомлений разработана так, чтобы предоставлять актуальную информацию и избегать избыточных оповещений:

-   **Уведомление о сбое**: При первом обнаружении проблемы (письмо пришло, а сделка не создалась) система отправляет email-уведомление об ошибке. Чтобы избежать повторных оповещений по одной и той же проблеме, `Message-ID` письма сохраняется, и повторные уведомления по нему блокируются.
-   **Новый сбой**: Если после этого приходит *новое* письмо, которое также не приводит к созданию сделки, система отправит новое уведомление, так как это уже другая проблема.
-   **Уведомление о восстановлении**: Как только система фиксирует первую успешную интеграцию (сделку) после периода сбоев, она отправляет уведомление о восстановлении работы.
-   **"Тихий" режим**: После отправки уведомления о восстановлении система переходит в штатный режим и больше не отправляет уведомлений об успешной работе, пока не произойдет новый сбой.

Состояние системы уведомлений (информация о сбоях и отправленных оповещениях) хранится в файле `notification_state.json`.

## Память об обработанных письмах

Чтобы не гонять повторные проверки одного и того же письма, служба хранит информацию об обработанных письмах в файле `processed_letters.json` (рядом с исполняемым файлом). Для каждого ящика запоминается последнее обработанное письмо: `Message-ID`, дата получения, отправитель и исход проверки (`deal_found` — сделка найдена, `no_deal` — сделка не создалась).

На каждом цикле, получив последнее письмо ящика, служба сравнивает его с записью в хранилище:

- письмо уже среди обработанных (новых писем с прошлого цикла не поступало) → проверка этого ящика **прекращается**, в лог пишется сообщение «уже обработано в предыдущем цикле»;
- письмо новое → выполняется обычная проверка интеграции, а по её завершении (успех или фиксация сбоя) письмо помечается как обработанное.

Сравнение делается по `Message-ID`; если сервер не отдал его, используется фолбэк по дате получения (совпадение с точностью до секунды). Файл перезаписывается атомарно (через временный `.tmp`-файл), поэтому не повреждается при сбое питания. Использовать SQLite или другую встраиваемую БД не потребовалось: объём данных — одна запись на ящик, а JSON-файл не добавляет зависимостей и читается любым текстовым редактором.

> Если нужно принудительно перепроверить письмо (например, после ручного вмешательства), остановите службу, удалите запись ящика из `processed_letters.json` (или файл целиком) и запустите службу снова.

## Конфигурация

Все настройки читаются через `IConfiguration` из трёх источников (в порядке возрастания приоритета):

1. **appsettings.json** — один файл рядом с приложением (без вариантов для окружений);
2. **User secrets** — локальные секреты разработчика (`dotnet user-secrets`);
3. **Переменные окружения** — для продакшена (например `MPIC__MonitoredMailboxes__0__Password`).

Пароли и строки подключения в репозиторий не коммитятся и в папке `Resources` не хранятся.

### Секция `MPIC` (MPIC/appsettings.json)

- `MonitoredMailboxes`: Список почтовых ящиков для мониторинга (логин, пароль).
- `NotificationSettings`: Настройки SMTP-сервера для отправки уведомлений.
- `Imap`: Настройки IMAP-сервера для чтения писем.
- `MaxTimeToCreateDealAfterLetter`: Максимальное время (в минутах), которое может пройти между получением письма и созданием сделки, чтобы интеграция считалась успешной.
- `RunIntervalMinutes`: Интервал (в минутах) между циклами проверки.
- `Username`, `Password`, `BaseApUrl`: Доступ к API Мегаплана (задаются в user secrets / переменных окружения).

### User secrets

Локально секреты задаются для проекта MPIC:

```sh
cd MPIC
dotnet user-secrets set "MPIC:MonitoredMailboxes:0:Password" "пароль_ящика"
dotnet user-secrets set "MPIC:NotificationSettings:SenderPassword" "пароль_smtp"
dotnet user-secrets set "MPIC:Username" "логин_мегаплан"
dotnet user-secrets set "MPIC:Password" "пароль_мегаплан"
```

## Ресурсы

- `Resources/Megaplan/Mapping/deal_mapping_rules.json` — правила нормализации полей сделки (копируются в выходную папку при сборке).
- Кэш токена Мегаплана пишется в `Megaplan/Token/` рядом с исполняемым файлом и не коммитится.
